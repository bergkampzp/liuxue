# 教师多维评价智能系统 — 方案说明

> 致北京某国际学校 | 2026 年 6 月
> 基于 2026-06-10 会议交流内容编写

---

## 一、我们理解的核心需求

在交流中，我们听到几个关键痛点：

> "每天都有数据，但给到家长的支持是什么？数据非常多，但家长不一定有时间去看……怎么让家长能更清晰地了解孩子的各方面情况？"

> "老师作为机器工作，可能愿意给一些助力——在应用上能起到作用。"

> "国际学校的本质是教育孩子，孩子的数据和信息是巨大的金矿。"

基于这些，我们理解贵校的核心诉求是：

**把学校已有的、分散在各 SaaS 系统中的教学数据，汇聚成可量化的教师评价体系，用数据而非主观印象来评估教学质量，最终服务于教师成长和学生发展。**

---

## 二、评价体系的构建逻辑

### 2.1 对标国际成熟框架

我们不从零想象，而是基于经过大规模实践验证的国际评价框架来设计。核心对标 **Danielson Framework for Teaching (FFT)**，这是美国超过 1000 个学区采用的教师评价标准，包含四大域、22 个评价组件：

```
┌─────────────────────────────────────────────────────┐
│              Danielson FFT 四大评价域                 │
├─────────────────┬───────────────────────────────────┤
│ Domain 1        │  教学设计                          │
│ Planning        │  教案的完整性、目标清晰度、          │
│ & Preparation   │  评估设计的合理性                   │
├─────────────────┼───────────────────────────────────┤
│ Domain 2        │  学习环境                          │
│ Learning        │  课堂氛围、学生管理、                │
│ Environments    │  师生互动质量                       │
├─────────────────┼───────────────────────────────────┤
│ Domain 3        │  教学实施                          │
│ Learning        │  提问技巧、学生参与度、              │
│ Experiences     │  反馈运用、差异化教学               │
├─────────────────┼───────────────────────────────────┤
│ Domain 4        │  专业素养                          │
│ Principled      │  教学反思、家校沟通、                │
│ Teaching        │  专业发展、同事协作                  │
└─────────────────┴───────────────────────────────────┘
```

### 2.2 从学校已有数据出发，减少主观打分

传统的教师评价依赖"问卷打分"和"主观印象"，存在三个问题：

| 问题 | 传统方式 | 我们的方式 |
|:---|:---|:---|
| 主观偏差 | 靠人工问卷和印象打分 | 用 SaaS 系统里客观的行为数据反推 |
| 打扰家长学生 | 每学期多次问卷，回收率低 | **零新增问卷**，从已有系统数据中提炼 |
| 数据孤岛 | 成绩、作业、考勤各自独立 | 汇聚到统一数据池，交叉分析 |

### 2.3 评价体系的三个层级

```
┌──────────────────────────────────────────────────────┐
│                    第三层：AI 洞察层                    │
│  大模型分析各维度间的隐藏相关性 → "某教师的作业反馈    │
│  质量提升后，学生成绩进步速度加快了 23%"               │
├──────────────────────────────────────────────────────┤
│                    第二层：评分计算层                   │
│  从系统数据中自动提取指标 → 归一化 → 加权聚合         │
│  17 个评价组件中 10 个全自动、4 个半自动               │
├──────────────────────────────────────────────────────┤
│                    第一层：数据汇聚层                   │
│  LMS 成绩 → 教务考勤 → 作业批改 → 学生评价记录 →      │
│  教案元数据 → 培训签到 → 家长沟通记录                  │
│  全部汇聚到统一的数据池                                │
└──────────────────────────────────────────────────────┘
```

**核心理念**：不是让老师填更多表，而是把学校已经在跑的系统数据用起来。当数据汇聚到数据池后，大模型可以发现人眼看不出的相关性——比如某个数据指标的变化往往预示着另一个指标的提升或下降。

## 三、如何从数据池构建教学评估模型

### 3.1 数据 → 指标 → 评分的自动化路径

以实际例子说明（基于 Danielson D4e — 学生成绩增值）：

```
传统的做法:
  教研组长翻看成绩表 → 凭印象说"这个老师教得不错" → 打分

我们的做法:
  LMS 系统导出各班级成绩数据
  → 自动计算每位教师所教学生的"进步率"
     (当前学期平均分 ÷ 上学期平均分 - 1)
  → 对照全年级/全学科基准线，计算偏离值
  → 大模型分析进步率与作业批改及时性、评语质量的相关性
  → 系统自动生成分项评分 + 文字说明
```

### 3.2 大模型的价值：发现隐藏相关性

学校有大量数据，但分散在多个系统中，人很难看到全局规律。大模型的核心价值是：

| 传统分析 | 大模型分析 |
|:---|:---|
| "这个班成绩下降了" | "这个班成绩下降与老师作业批改周期从 2 天延长到 5 天存在 0.73 相关性，同时学生评价记录中'听不懂'类词汇增加了 40%" |
| "这位老师很负责" | "该教师家长沟通频次排名前 15%，平均响应时间 2.3 小时，且沟通内容中'进步''表现好'等正向词汇占比 67%" |
| "课堂氛围不错" | "从学生日常评价记录中，该教师所教班级的积极情感词占比 72%，高于全校均值 58%" |

**大模型不是替代人的判断，而是为人的判断提供数据证据。** 最终等级仍由教研组长和校长共同确认。

### 3.3 评价流程闭环

```
┌─────────────────────────────────────────────────────────┐
│                                                          │
│  ① 系统数据自动采集                                       │
│     LMS/教务/SaaS/沟通平台 → 每日/每周定时同步             │
│                          ↓                               │
│  ② 数据池清洗与结构化                                     │
│     多源格式统一 → 师生关联 → 去标识化脱敏                  │
│                          ↓                               │
│  ③ 大模型分析引擎                                         │
│     自动计算指标 → 情感词频分析 → 相关性发现               │
│                          ↓                               │
│  ④ 评价看板输出                                           │
│     教师雷达图 + 校长总览 + 异常预警 + 改进建议             │
│                          ↓                               │
│  ⑤ 人工确认（仅 3 张结构化表单）                           │
│     教研组长课堂观察 + 教师自评 + 同事互评                  │
│                          ↓                               │
│  ⑥ 评价报告生成                                           │
│     个人发展报告 → 教研指导 → 学期总结                      │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

## 四、实施路径

### 4.1 第一阶段：需求细化与数据摸底（2-3 周）

| 步骤 | 内容 | 需要学校配合 |
|:---|:---|:---|
| **系统调研** | 逐一确认学校现有 SaaS 系统的数据格式、接口方式、数据字典 | 提供系统清单 + 对接人 |
| **数据摸底** | 抽取一个班级/一个科目的样本数据，验证数据质量和完整性 | 提供样本数据访问权限 |
| **评价维度确认** | 基于 Danielson 框架，与校方确认各维度的权重和调整项 | 教研组长/校长参与讨论 |
| **模型训练准备** | 基于样本数据训练基础的情感分析模型和指标计算模型 | — |

### 4.2 第二阶段：MVP 构建（2 周）

| 步骤 | 内容 | 产出 |
|:---|:---|:---|
| **数据对接** | 完成 3-5 个核心系统的数据接入 | 数据管道 + 数据字典 |
| **评价引擎** | 实现自动评分计算 + 手动表单 | API 服务 |
| **看板搭建** | 教师个人看板 + 校长总览看板 | Web 应用 |
| **试点部署** | 在 2-3 个教研组内试点使用 | 部署文档 + 使用手册 |

### 4.3 时间线总览

```
Week 1-2:  系统调研 + 数据摸底 + 维度确认
Week 3:    模型训练 + 评价引擎开发
Week 4-5:  数据对接 + 看板开发 + 试点部署
Week 6:    根据试点反馈调整 + 交付
```

**总计约 6 周，1-2 名工程师即可完成 MVP 交付。**

## 五、技术架构与安全合规

### 5.1 基于云计算降低成本

| 层级 | 方案 | 成本特点 |
|:---|:---|:---|
| **计算** | 云服务器（阿里云/腾讯云教育专区） | 按需付费，无需学校自建机房 |
| **存储** | 云数据库 + 对象存储 | 弹性扩容，随数据量增长 |
| **AI 能力** | 云端大模型 API（DeepSeek/通义千问等） | 按调用量计费，单次分析成本几分钱到几毛钱 |
| **部署** | Docker 容器化 | 一套配置多处部署，降低运维成本 |

### 5.2 数据安全：三道防线

学校最关心的数据安全问题，我们设计三道防线：

```
┌──────────────────────────────────────────┐
│          第一道防线：数据脱敏               │
│                                          │
│  学生姓名 → 匿名 ID                       │
│  原始成绩数据 → 仅保留统计值和趋势          │
│  沟通记录 → 仅保留情感词频，不保留原文       │
│  视频数据 → 边缘处理，不在云端存储原始视频    │
├──────────────────────────────────────────┤
│          第二道防线：访问控制               │
│                                          │
│  校长：可查看全校聚合数据                   │
│  教研组长：仅可查看本组教师数据              │
│  教师本人：仅可查看自己的报告               │
│  家长/学生：不参与评价系统（零数据接触）      │
├──────────────────────────────────────────┤
│          第三道防线：传输与存储加密          │
│                                          │
│  TLS 1.3 加密传输                         │
│  数据库静态加密（AES-256）                 │
│  操作日志全量审计                          │
│  符合《个人信息保护法》《数据安全法》要求     │
│  符合《未成年人保护法》对未成年人数据的       │
│    特殊保护要求                            │
└──────────────────────────────────────────┘
```

### 5.3 安全架构简图

```
学校内网                          云端（阿里云/腾讯云教育专区）
┌─────────────┐                  ┌──────────────────────┐
│ LMS 系统    │ ──API(只读)──→   │                      │
│ 教务系统    │ ──API(只读)──→   │   数据脱敏网关         │
│ 教案系统    │ ──API(只读)──→   │   (去标识化处理)       │
│ 沟通平台    │ ──API(只读)──→   │        ↓              │
│             │                  │   评价计算引擎         │
│ 录播系统    │ ──(Phase 2)──→   │   (仅处理脱敏后数据)   │
│             │                  │        ↓              │
│             │                  │   Web 看板服务         │
│             │  ←──HTTPS───    │   (角色权限控制)       │
│ 浏览器      │                  │                      │
└─────────────┘                  └──────────────────────┘

关键原则：
• 学校系统只提供只读接口，不修改原始数据
• 视频数据在 Phase 2 才接入，且在接入层即完成脱敏
• 所有 AI 分析在云端完成，但处理的都是脱敏后的数据
• 原始数据不出学校内网
```

## 六、与传统评价方式的对比

| 维度 | 传统方式 | 本方案 |
|:---|:---|:---|
| **数据来源** | 人工问卷 + 印象打分 | SaaS 系统自动采集的行为数据 |
| **主观性** | 高（问卷填写率和质量不稳定） | 低（客观行为数据为主，手动表单仅 3 张） |
| **对家长学生的打扰** | 每学期多次问卷 | **零**（不新增任何问卷） |
| **评价周期** | 期末一次性 | 持续性（数据每日更新，随时可看趋势） |
| **发现问题的能力** | 问题出现后才知道 | 异常预警（成绩下滑等趋势提前发现） |
| **对教师的赋能** | "被考核"的感受 | "看到自己的成长轨迹"的体验 |
| **成本** | 人力成本（教研组长大量时间翻数据） | 系统成本（单次分析几分钱到几毛钱） |

## 七、下一步

我们建议：

1. **确认合作意向**，安排一次 30 分钟的线上会议，逐项确认学校现有系统清单

2. **签署数据安全协议**，明确数据采集范围、脱敏标准和访问权限

3. **启动系统调研**（1-2 周），我们派工程师到现场或远程对接各系统接口

4. **确认评价维度**，基于 Danielson FFT 框架，与教研组长/校长讨论适配和权重

5. **启动 MVP 开发**（4-5 周），交付第一个可用版本供试点
